### Summary

<Callout id="summary" tone="warning">

**The defect.** A sweep pass reads its candidates, then deletes each one by id without looking at the row again. So a memory that another session pins or reinforces during the pass can still be deleted, while `Reinforce` and `Pin` tell their caller OK. A `remember` that dedups onto such a row answers `deduped: true`, and its content is stored nowhere.

**The fix.** The sweep deletes through a new `DeleteIfStale`, which takes the row's write lock first and only then re-checks that the row is unpinned and still last accessed before the cutoff. `Reinforce`, `Pin` and `SetForgotten` match the row again after their write and return `engram.ErrNotFound` when it is gone. `remember` then stores the content as a new memory. `recall` still returns the vanished hit, skips its reinforcement and propagation, and logs it at debug level.

</Callout>

This is not a new milestone. It corrects M4 (PRD section 9: scheduled sweep, reinforcement, `forget` and pin) and restores PRD section 6.3, "Pinned memories are exempt". It is post-M6 cleanup, after `sweep-on-start`. The race is as old as M4's sweep. Since PR #38 a pass runs one minute into every session, so ordinary sessions now reach it. It is rare, silent and permanent.

**The eval does not move.** Inside the eval one goroutine drives the store, so the re-check is always true. The gate runs right after the sweep task, and any difference stops the work.

The defect has two halves.

**The delete does not look again.** The candidates are a snapshot. `Delete` (`neo4j/store.go:412`) is `MATCH (m:Memory {id: $id}) WITH m, count(m) AS c DETACH DELETE m RETURN c`. It does not look at the row, so a row pinned or reinforced after the read is deleted all the same.

**The writers report success on a row that is gone.** `Reinforce` (`neo4j/store.go:180`) and `Pin` (`:384`) are `MATCH ... SET ... RETURN count(m)`. When the row is deleted while they wait for its lock, the `SET` is a silent no-op and the count is still 1. They return nil for a row that is gone. `remember` then answers `deduped: true` while the content is stored nowhere.

### Why a WHERE on the delete is not enough

The obvious fix is to add the stale predicate to the delete, as `MATCH ... WHERE ... DETACH DELETE`. It does not work. Neo4j evaluates `MATCH` and `WHERE` before it takes the row's write lock, so the `WHERE` reads the row as it was before a concurrent writer committed.

<Callout id="where-probe" tone="info">

**Measured on the live Neo4j 5.26.** A conditional delete written as `MATCH ... WHERE ... DETACH DELETE` still deleted the row in about 95% of overlapping rounds, after the writer had been told it succeeded.

</Callout>

The Neo4j Operations Manual documents this problem and its fix: "Concurrent data access", "Lost updates", example "Dummy property to acquire a write lock" (`https://neo4j.com/docs/operations-manual/current/database-internals/concurrent-data-access/`). Neo4j takes a node's write lock when a statement first writes to it, not when it matches it. A statement that writes a dummy property first waits for any writer that got there earlier, and what it reads after that write is committed. D1 uses this form.

### The fix

design.md has eight decisions. D1 to D6 are below; D7 (the tests) is under "The evidence" and "Tasks", and D8 (the eval) is under "The eval". No new package and no new interface. `sweep.Pruner` swaps one method, so it stays at two.

A code comment explains the `SET` and `REMOVE` pair and cites the manual section. Without it the pair reads as dead code, and the next cleanup removes it.

Two other forms were tried:

- **The predicate between the `SET` and the `REMOVE`.** An earlier draft. Both forms gave the same result in every probe cell: stale deleted, fresh kept, pinned kept, missing id 0, no property left behind, no lost write. The shorter one is the documented one, so it is kept.
- **`SET m.id = m.id`.** It also took the lock in the probe. It is rejected: it writes the property the uniqueness constraint covers, and a no-op `SET` taking the lock is observed behaviour, not documented.

**Cost.** 7 to 9 ms median per call in the probe, against 9 ms for the unconditional `Delete`. No measurable difference.

**Why this re-check is complete.** Only three writers can turn "delete" into "keep": `Pin` (retrievability becomes 1), and `Reinforce` and `PropagateReinforce` (`last_accessed` becomes now). `Supersede` only lowers stability, and `SetForgotten` does not feed decay, so neither can. No handler overwrites a row with `Put`. So "unpinned and `last_accessed` before the cutoff" is a complete re-check.

The increment now reads `access_count` after the lock is held. That is the form the manual gives against a lost update between two concurrent `Reinforce` calls. That pairing was not probed, and the plan does not claim it.

**Left alone.** `PropagateReinforce` and `Supersede` never tell a caller that one given row was written. The first is best effort over neighbours, and the second returns nil for absent ids.

**`SetForgotten` goes beyond the defect.** A soft forget of a deleted row harms no one. It is included because it shares `flagOne` with `Pin`, and `mcp/forget.go` promises a legible not-found for soft, hard and pin alike. So `forget` with mode pin or soft now answers "memory not found" for a row deleted under it.

### What this change does not fix

- Coordinating passes between processes. That is `sweep-daily-claim`, the once-a-day gate, which follows this change.
- Which rows are candidates, the grace period, the floor and the batch size.
- Consolidation: trying another dedup candidate, or merging, when the first is gone. The PRD defers it to v2.
- A counter of rows the sweep kept, and a retry loop on `Reinforce`.
- The message of `forget` for a pruned memory (open question 1).
- `PropagateReinforce` and `Supersede`: neither tells a caller that one given row was written.
- A hard `forget` deletes whatever it names, including a row another session has just reinforced or pinned, because the agent asked for exactly that.
- Ordering or paging `PruneCandidates`, and stopping a pass when its context is cancelled. Both are listed follow-ups from `sweep-on-start`.

Two gaps are disclosed and stay open:

- **An auto-link whose target is deleted mid-statement.** `Link` skips a target deleted before its statement starts, in both stores (`neo4j/store.go:249`, `mock/memstore.go:146`). A target deleted while the statement runs is different: `Link` returns `Neo.ClientError.Statement.EntityNotFound`. The content is stored before `Link` runs, so the agent sees `remember: store unavailable` after a successful insert, and `supersedes` is not applied by that call. A retry dedups onto the stored memory and applies it. This is not new. Over 100 overlapping rounds, run twice, `Link` failed in 65 and 66 rounds against the unconditional delete on `main`, and in 62 and 58 against the lock-first delete. This change neither adds nor removes it (open question 3).
- **A near-duplicate.** When the target is gone and a second live candidate also scores at or above 0.95, the content is stored as a new memory, auto-linked to that candidate. This needs the race and two candidates above the dedup point at once (open question 4).

<Callout id="unrecoverable" tone="warning">

**Rows lost to this race before the fix cannot be found.** `DETACH DELETE` leaves no tombstone, and the sweep logs no id on a successful delete, so the affected memories cannot be listed. Nothing suggests it has happened: the precondition is a write to a row that is past the 30-day grace and below the floor, inside the length of one pass. The proposal and the PR body disclose it. Reverting the PR brings the race back; it loses nothing by itself.

</Callout>

### The eval

`SweepOnce` will call `DeleteIfStale` on `mock.MemStore`. Inside an eval arm the re-check is true for every candidate:

- one goroutine drives the store;
- `PruneCandidates` returns unique ids in insertion order;
- nothing under `eval/` pins a row between the two calls;
- one `before` feeds both.

So the same rows are deleted, and the same count is returned. The real risk is the cascade. If `DeleteIfStale` deleted a row differently from `Delete`, the edge and bridge counts in the table would move. D6 removes that risk, because both methods share `deleteLocked`.

No eval constant, mix, weight, threshold or dataset size is touched, so there is nothing to preregister. The prediction: `go run ./cmd/eval --ci` passes, the type-aware precision and nDCG are the 0.179 and 0.875 of `eval/baseline.json`, and every figure of every arm equals `main`'s output once the two wall-clock columns (p50, p95) are removed. No code under `eval/` or `cmd/eval/` calls `Run`. The check runs in Task 2.2 and again in Verify on the final tree.

One spec sentence about the eval is reworded, and nothing about the eval itself changes. The scenario "Gate with zero drift" said "every A/B/C figure equals the baseline exactly". `eval/baseline.json` holds only the type-aware precision (0.1788) and nDCG (0.8747), so that sentence could not be checked as written. It now says what the check does: the two type-aware figures equal the baseline at the three decimals the report prints, and every figure of every arm equals `main`'s output.

### Summary

`Sweeper.Run` waits one full tick before its first pass, and `cmd/engramd` sets the tick to one hour. An agent host starts `engramd` for one session and stops it when the session ends, usually inside the hour, so the hard-prune that M4 shipped rarely runs in real use.

After this change, `Run(ctx, firstDelay)` runs one pass when `firstDelay` has elapsed, then one pass per interval. `engramd` passes one minute, so the first pass runs one minute after start and then hourly. This is not a new milestone. It corrects the scheduled sweep of M4 (PRD section 9) as post-M6 cleanup.

**The eval does not move.** The eval calls `sweep.New` and `SweepOnce` with virtual time and never calls `Run` (`eval/arm.go:215-217`). `New` keeps its signature, and `SweepOnce` returns the same count and error for every input.

Franco answered the open questions on 2026-11-15. The Decisions section at the bottom records them.

<Callout id="backlog-warning" tone="warning">

**This change makes hard-prune real for the first time, and the first pass deletes the backlog permanently.** A pass hard-deletes every unpinned memory idle more than 30 days whose retrievability is below 0.02, in every namespace, up to 500 candidates per pass. A read-only count on the dev store on 2026-11-15 found 164 candidates. A pass would delete 163 of them (118 semantic, 45 episodic) and keep 1 semantic row still above the floor. All 164 sit in the `m1-*` to `m4-*` namespaces the `mcp` integration tests create. No row outside a test namespace is a candidate today. Every integration run before the fixture edits adds more rows of the same kind.

The pass runs one minute into the first session started with a rebuilt `engramd`, not at merge. Soft-forgotten and superseded rows go by the same rule, and once a pass deletes them, `include_forgotten` cannot bring them back. Reverting the PR restores no row. Franco agreed on 2026-11-15 that this pass may run on the dev store.

</Callout>

### When the first pass runs

Three schedules were weighed. The table shows what each one does for the kinds of process that exist.

**Decided: one minute, then hourly.** `cmd/engramd/main.go` gains `sweepFirstDelay = time.Minute` next to `sweepInterval`, passes it to `Run`, and adds it to the startup log line as `sweep_first_delay`. There is no flag and no environment variable.

**Why not zero.** A host that starts the server only to list its tools would start a pass and abandon it, and a pass cut off by a cancelled context logs an error for each remaining candidate. `TestStdioAllTools` starts two real `engramd` processes while other packages' integration tests use the same Neo4j. With a pass at start, the suite itself would delete any future fixture that is old and decayed, at random. A pass at start also competes with the session's first tool calls.

**Why not ten minutes.** It is the cheapest fix, and it works for long sessions. It moves the first pass by changing the cadence, so the two cannot be set apart. Ten minutes still misses sessions under ten minutes, and a first pass at one minute would mean a store scan every minute for the life of every process.

**What the delay costs.** A session shorter than a minute never prunes. A row becomes prunable only after 30 idle days, so the next longer session is soon enough. One minute is a judgement, not a measured optimum: it is long against the integration suite's 5.4 seconds and short against a working session.

**The cadence stays hourly in this change.** Franco also wants at most one pass a day for the whole store. That needs state shared between processes, kept in Neo4j, so it is the next change, `sweep-daily-claim`. It keeps the hourly tick as the moment each process tries.

### How `Run` changes

The delay is an argument to `Run`, not a field set by `New`. The delay matters only to `Run`, which has one caller (`cmd/engramd/main.go:81`). `New` already takes eight positional arguments and has three callers, and one of them is the eval, which this change must not touch.

The schedule stays off `engram.Clock`. Moving it there would add a timer method to a domain port that the decay math and the eval use only for `Now()`, to serve one goroutine. `sweep/sweep.go` contains no `time.Now` call before or after the change.

Inside `synctest.Test`, timers use a fake clock that advances only when every goroutine in the bubble is blocked. A test can then assert no pass one nanosecond before the delay and one pass at the delay without waiting in real time. `testing/synctest` has been in the standard library since Go 1.25, and `go.mod` says 1.26. The schedule tests were dry-run in a scratch copy of `main`: the first one fails on the old behaviour with `at the first delay: 0 passes, want 1`, all of them pass after the change, and three consecutive `-race` runs are green.

Running passes in ordinary sessions brings three existing behaviours into play. The next three sections cover them.

### A row that is already gone

A pass reads its candidates, then deletes them one by one. A row can vanish in between, because another process's pass got to it first or the agent hard-forgot it. `Delete` then returns `engram.ErrNotFound`, and today each such row writes `sweep: delete failed` at error level to the host's MCP log. Before this change, two processes sweep the same rows only if both live past the hour. After it, any two sessions that start close together do. `SweepOnce` now skips the row quietly.

<Callout id="delete-probe" tone="info">

**Probed against the live Neo4j.** In 200 rounds of two exactly overlapping deletes of one row through one driver, and 200 through two drivers, both callers got success, no call returned an error, and no row was left behind. Overlapping passes are safe. `ErrNotFound` is the outcome only for a pass that arrives after the other one has committed, or after a hard forget.

</Callout>

`SweepOnce` returns the same count and the same error as before for every input. A failed delete was already skipped and not counted; the one difference is that this error is no longer logged. Two consequences are accepted. The skipped row is not counted, and `LastPruned` and `TotalPruned` stay per process. When two deletes overlap exactly, both processes count the row, so across processes the counts can add up to more than the rows removed.

### The stdio test and the tool description

`TestStdioAllTools` asserts `sweep.last_run_at` is null on the real binary. With a one-minute delay it would still pass, by a margin of timing and nothing else. It becomes a shape check:

- `last_run_at` is null or a string that parses as RFC 3339.
- `last_pruned` and `total_pruned` are numbers, zero or more.
- If `last_run_at` is null, both counts are 0.

It also asserts that the startup log of process `a` contains `sweep_first_delay=1m0s` and `sweep_interval=1h0m0s`. The exact null-and-zero wire shape stays pinned in `mcp/stats_test.go`, which injects the stats function and asserts the JSON. Every other test that expects empty stats either never starts `Run` or injects a stats function, so none of them changes.

The stats contract does not change: `sweep.last_run_at` is null until a pass completes, and the counts are 0. The `memory_stats` description changes one sentence.

<Callout id="store-search-risk" tone="info">

**`TestStoreSearch` broke on the dev volume, and that blocked a green integration run. It is cleared.** The cause is unrelated to this change. The `neo4j` and `sweep` integration tests write rows with the same one-hot embedding on every run and never remove them. `Search` asks the vector index for the 50 nearest rows store-wide and filters by namespace afterwards. With 512 identical vectors in the store, the test's new row was rarely among the 50, and the filter left nothing.

On 2026-11-15, with Franco's agreement, the 684 rows in `itest-*` and `sweep-*` namespaces were deleted, and the test passes again. It will come back after enough runs. Making those tests clean up after themselves, and the store-wide-then-filter search behind the failure, are listed for Franco as follow-ups.

</Callout>

### Out of scope

- A flag or environment variable for the first delay or the interval.
- Persisting the time of the last sweep, or coordinating passes between processes. That is the next change, `sweep-daily-claim`.
- Per-namespace sweep behaviour, which is v2.
- Ordering or paging `PruneCandidates`, the candidate cap listed in Risks.
- Stopping a pass early when its context is cancelled.
- Changing the grace period, the floor, the batch size or the decay model.
- A sweep at shutdown.
- Making `TestStoreSearch` robust against leftover rows, listed in Risks.
